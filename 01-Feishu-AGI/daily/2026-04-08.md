系统工程：构建真正可用的 Agentic 软件

原帖链接：https://x.com/ashpreetbedi/status/2041568919085854847

image.png

在 1940 年代早期，贝尔实验室正在建设全国电话网络，那是当时世界上最复杂的技术系统。数百万个交换机、电缆、继电器和接线员必须协同工作。工程师们发现了一件后来成为 80 年经验教训的事：你无法通过优化单个组件来优化整个系统。系统整体的行为（呼叫路由、可靠性、容量、成本）取决于各部分如何相互作用。他们需要一门专注于组件之间交互的学科。
他们称之为系统工程。

软件工程即系统工程
Agentic software 生态系统正在重复当年催生这门学科时犯下的同样错误。当前这波 harness engineering 会让你用文件系统来做存储和记忆，然后再试图通过在数据库之上构建一个虚拟文件系统来绕开它的限制。它会让你把 bash 当作通用工具，然后为了安全再强迫你进入按请求隔离的 sandbox。这些都是在没有从系统整体角度考虑的前提下，只优化某个局部所产生的症状。而我们正在照单全收，却没有花一分钟去问：这真的是正确的方法吗？
Coding agents 确实降低了写代码的门槛，但它们并没有降低生产级软件的要求。软件工程本质上一直都是系统工程；如果你正在构建 agentic software，那么你的系统就需要打通这五层：
Agent Engineering：你的 agent 或 multi-agent 逻辑与执行流。
Model、system instructions、tool configurations、handoffs、context management、observability。这里定义的是你的 agent 做什么、如何运行，以及如何响应。你的 agent 行为在可能的地方应当是确定性的，在不能确定的地方应当是可观测的。
Data Engineering：你的 agent 能力上限取决于它可以访问的上下文，而上下文本质上就是数据。Memory、storage、knowledge，都应该用数据工程原则来管理。这意味着设计良好的 schema、结构化查询、适合快速读写的数据库、适合长期存储的对象存储，以及让知识和记忆始终保持最新的 pipeline。这些模式已经存在几十年了。拿来用。
Security Engineering：Auth、RBAC、governance、data isolation、audit trails。
你的 agent 能做什么，是由它的工具决定的，而这些工具应该通过 JWT 支撑的权限来进行作用域控制。只读访问不是一条 prompt instruction，它是一项 tool configuration。操作应当有审批分级：读取可以自由执行，写入需要用户批准，敏感操作需要管理员签字。大多数操作都应该被记录，并且在产品生命周期内可查询。
另外，请务必隔离请求。一个用户的上下文泄漏到另一个用户那里，这不是 bug，而是数据泄露。它会带来严重后果，而且有法律专门保护用户数据。所以，在共享 sandbox 上用文件系统支撑 memory，也许并不是个好主意。
Interface Engineering：用户和其他 agents 如何接入你的 agent。
REST API、Slack、MCP server、terminal。在旧世界里，你只有一个 API 和一个 client。现在你有多个 surface，而每个 surface 都有自己的 identity system。Slack 用户 ID 不是你产品里的用户 ID。一个以另一个 agent 身份认证的 MCP client 也不是人类用户。Interface engineering 的任务，就是确保无论你的 agent 从哪个 surface 被访问，你的 auth、policy 和 access control 都能保持一致。
Infrastructure Engineering：你如何运行和扩展你的软件。Containers、cloud deployment、horizontal scaling。通常这被称作 DevOps。
好消息是：其中 95% 和运行其他任何服务完全一样。复用现有模式，它们会很好地服务你。那 5% 的差异在于：agent 请求耗时更长（提高 load balancer timeout），响应是流式的（为 SSE 或 WebSockets 做规划），而最好的 agents 是主动型的（scheduled tasks、background execution）。这些都不新鲜。

贝叶斯定理：AI 决策背后的秘密

原帖链接：https://x.com/TheVixhal/status/2041568489220272424
image.png

贝叶斯定理是概率论和机器学习中的一个核心思想。它告诉你，当你看到新数据之后，应该如何更新自己的判断。
在这篇文章里，我们会把整个内容一块一块拆开来讲。你最终会明确获得这些内容：
贝叶斯定理到底是什么意思（用通俗英语讲，不用教科书折磨人）
形式化的数学定义（因为没错，考试确实存在）
一个能让你一下子理解的现实生活例子
一个完整的数值题，逐步求解
这个东西到底会在 AI 和机器学习里的哪些地方出现
可以吗？那我们开始。

首先，现实生活中的直观理解
在碰任何公式之前，我们先用一个故事建立一点直觉：假设你查看钱包，发现少了一些钱。你会想：“是不是有人偷了它？”
然后你的大脑，即便你自己没有意识到，也会开始做一些快速计算。
你知道：
你之前去过一个很拥挤的市场。
你听说过在这种地方会发生扒窃。
但也有可能，你只是忘了把钱花在了哪里，或者是自己放错了地方。
所以你的大脑其实是在权衡证据（钱不见了）和你原本对世界的认知（拥挤场所会增加被盗风险，但自己弄错也会发生）。基于这一切，你会更新自己对“这钱到底是不是被偷了”的判断。
这就是贝叶斯定理在发挥作用。它只是把这句话正式化了：
“基于新的证据，更新你的信念。”

严谨的数学定义
好，接下来我们短暂戴上教科书的帽子。
贝叶斯定理给了我们一种方法，用来计算：在观察到某些证据（E）的条件下，一个假设（H）成立的概率。公式长这样：
P(H|E) = (P(E|H) × P(H)) / P(E)
我们把每一部分拆开来看：
image.png

你可以这样理解它：
Posterior = (Likelihood x Prior) / Evidence
你一开始有一个判断（prior），然后你看到了某件新事情发生（evidence），接着你更新自己的判断（posterior）。这就是贝叶斯定理做的全部事情。

现实案例：垃圾邮件问题
假设你正在构建一个基础的垃圾邮件过滤器。你收到一封邮件，里面包含单词 “lottery”。你想知道的是：在已知这封邮件包含 “lottery” 的前提下，这封邮件是垃圾邮件的概率是多少？
用贝叶斯记号来写：
P(Spam | "lottery") = (P("lottery" | Spam) × P(Spam)) / P("lottery")
这里是我们已知的数据：基于新证据更新你的判断。
假设我们查看了过去的 1000 封邮件，并得到了这些数字：
1000 封邮件里有 400 封是垃圾邮件。所以 P(Spam) = 400/1000 = 0.40
1000 封邮件里有 600 封不是垃圾邮件。所以 P(Not Spam) = 600/1000 = 0.60
在 400 封垃圾邮件里，有 120 封包含单词 “lottery”。所以 P(“lottery” | Spam) = 120/400 = 0.30
在 600 封非垃圾邮件里，只有 18 封包含单词 “lottery”。所以 P(“lottery” | Not Spam) = 18/600 = 0.03

第一步：计算P(“lottery”)
这就是任意一封邮件包含单词 “lottery” 的总概率，不管它是不是垃圾邮件。这里我们会用到全概率公式：
P("lottery") = P("lottery"|Spam) × P(Spam) + P("lottery"|Not Spam) × P(Not Spam)

代入数值：
P("lottery") = (0.30 × 0.40) + (0.03 × 0.60)
P("lottery") = 0.12 + 0.018 = 0.138

第二步：将所有数值代入贝叶斯公式
P(Spam|"lottery") = (0.30 × 0.40) / 0.138
P(Spam|"lottery") = 0.12 / 0.138
P(Spam|"lottery") ≈ 0.8696


第三步：解读结果
如果一封邮件包含单词 “lottery”，那么它大约有 87% 的概率是垃圾邮件。
在看到 “lottery” 这个词之前，我们认为任意一封随机邮件是垃圾邮件的概率是 40%（我们的 prior）。但在看到这个证据之后（单词 “lottery”），我们的判断一下子跳到了大约 87%。这是一次很大的更新，而且这很合理，因为垃圾邮件比普通邮件更喜欢使用这个词。
这就是贝叶斯的美妙之处。它把我们原本的直觉判断（40% 是垃圾邮件）和实际证据结合起来，给出了一个更锐利的答案（87% 是垃圾邮件）。
